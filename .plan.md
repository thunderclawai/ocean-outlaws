# Plan: Remove all procedural geometry fallbacks — FBX models are required

## Issue
#158 — Remove procedural geometry fallback code for ships, enemies, and bosses. Failed loads show a debug error placeholder instead of silently falling back.

## Analysis

The codebase currently has a two-tier model loading strategy: each entity starts with procedural Three.js geometry, then asynchronously attempts to load a GLB model override. If the GLB load fails, the `.catch()` handler silently keeps the procedural mesh. This masks loading bugs.

**Key files with procedural fallbacks:**

- **`game/js/ship.js`** — `buildShipMesh()` (lines 30-80) creates a fallback procedural ship. `createShip()` (line 116) falls back to this when no `classConfig.key`. `applyShipOverrideAsync()` (line 104) silently catches GLB load failures.
- **`game/js/shipModels.js`** — `buildClassMesh()` and four `build*Mesh()` functions (destroyer, cruiser, carrier, submarine) build procedural ship-class geometry. These are used as the initial mesh before async GLB swap.
- **`game/js/shipParts.js`** — Shared materials/detail builders consumed only by `shipModels.js`. Will become unused if procedural models are removed.
- **`game/js/bossModels.js`** — `buildBossMesh()` and three `build*Mesh()` functions (battleship, carrier, kraken) build procedural boss geometry.
- **`game/js/enemy.js`** — `buildEnemyMesh()` (lines 118-185) creates procedural enemy patrol boat. `applyEnemyOverrideAsync()` (line 200) silently catches failures.
- **`game/js/boss.js`** — `applyBossOverrideAsync()` (line 105) silently catches failures.
- **`game/js/netSync.js`** — `createRemoteShipMesh()` (line 128-142) uses `buildClassMesh()` as initial placeholder before async GLB swap.

**Current model manifest (`game/assets/manifest.json`):**
- All 4 player ship classes mapped (destroyer→sloop.glb, cruiser→brigantine.glb, carrier→galleon.glb, submarine→manowar.glb)
- `enemy_patrol` → enemy-patrol.glb
- `boss_battleship` → boss-blackthorn.glb, `boss_carrier` → boss-widow.glb
- Kraken has no GLB model entry (no `boss_kraken` slot)

**Terrain:** Already fully migrated to composition-field visuals in `terrain.js`/`terrainComposite.js` via prior PRs (#147, #173, #174). No procedural terrain fallbacks remain. The only "fallback" is `addTieredIslandFieldVisual` which is a secondary composition approach, not legacy procedural geometry. No changes needed.

## Changes

### game/js/ship.js (modify)
- **Delete `buildShipMesh()` function** (lines 29-80): Remove the entire fallback procedural ship geometry builder.
- **Modify `createShip()` (line 111-122)**: Remove the `else` branch (line 116) that falls back to `buildShipMesh()`. When no `classConfig.key`, use a simple error placeholder instead. However, in practice `createShip` is always called with a `classConfig` from `main.js`, so this path should simply create a placeholder group.
- **Modify `applyShipOverrideAsync()` (line 83-107)**: Change the `.catch()` handler (line 104-106) from silently keeping the procedural fallback to: (1) logging `console.error("Failed to load ship model: " + path)`, and (2) replacing the mesh children with an error placeholder (bright magenta box).
- **Add `createErrorPlaceholder(size)` helper** near top of file: Returns a `THREE.Mesh` with `BoxGeometry` and bright `MeshBasicMaterial({ color: 0xff00ff })` — a visible debug indicator. Include fire points so turret code doesn't break.

### game/js/enemy.js (modify)
- **Delete `buildEnemyMesh()` function** (lines 118-185): Remove entire procedural enemy patrol boat builder.
- **Delete `getFactionMats()` and `factionMats` cache** (lines 103-115): Only used by `buildEnemyMesh`.
- **Delete faction color properties** from `FACTIONS` object (lines 13-14, 20-21, 27-28): `hullColor`, `deckColor`, `bridgeColor`, `glassColor` — only used by procedural mesh. Keep all gameplay-relevant properties (speed, hp, etc).
- **Modify `spawnEnemy()` (line 292-293)**: Replace `buildEnemyMesh(faction)` + `applyEnemyOverrideAsync(mesh)` with a new approach: create a placeholder group, load GLB model directly. Create fire points on the placeholder group so firing works even before model loads.
- **Modify `spawnAmbientEnemy()` (line 333-334)**: Same change as `spawnEnemy()`.
- **Modify `applyEnemyOverrideAsync()` (lines 187-203)**: Change `.catch()` from silent fallback to `console.error` + error placeholder. Or inline this logic into spawn functions to avoid needing a separate "apply" step.

### game/js/boss.js (modify)
- **Modify `createBoss()` (line 121)**: Replace `buildBossMesh(bossType)` with a placeholder group that has the correct fire points and tentacle attachment points. Load GLB async.
- **Modify `applyBossOverrideAsync()` (lines 85-108)**: Change `.catch()` to log `console.error("Failed to load boss model: " + path)` and show error placeholder.
- **Handle Kraken**: Kraken has no GLB model in manifest (`boss_kraken` slot missing). After removing procedural fallback, kraken will show the error placeholder. This is acceptable — it makes the missing asset visible rather than hiding it.

### game/js/shipModels.js (modify)
- **Replace procedural builders with placeholder logic**: `buildClassMesh(classKey)` should return a simple placeholder group (empty group with fire points at default positions) instead of procedural geometry. This is still used as the initial mesh before GLB loads. Keep it lightweight — just an empty group with fire points so turrets work.
- **Delete** `buildDestroyerMesh()`, `buildCruiserMesh()`, `buildCarrierMesh()`, `buildSubmarineMesh()` functions (lines 10-294).
- **Remove imports** from `shipParts.js` (line 3-7) since no procedural details are needed.
- **Add a simple `buildPlaceholderMesh()` function** that creates a group with generic fire points (port, starboard, bow) and a small error-placeholder box.

### game/js/bossModels.js (modify)
- **Replace procedural builders with placeholder logic**: `buildBossMesh(bossType)` returns a placeholder group with fire points and tentacle attachment points (for kraken).
- **Delete** `buildBattleshipMesh()`, `buildCarrierBossMesh()`, `buildKrakenMesh()` functions (lines 56-349).
- **Delete** shared boss materials and detail helpers (`ensureBossMats`, `addBossNavLights`, `addBossRadar`, `addBossWindows`) (lines 5-53).
- **Add a minimal `buildBossPlaceholder(bossType)` function** that creates a group with: (1) fire points matching expected positions for each boss type, (2) tentacle groups for kraken (empty groups at correct positions for animation), (3) magenta error box for visibility.

### game/js/shipParts.js (modify or delete)
- **Evaluate**: After removing procedural models from `shipModels.js`, check if anything else imports from `shipParts.js`. If nothing does, **delete the file entirely**.
- Search result confirms: only `shipModels.js` imports from `shipParts.js`. **Delete this file.**

### game/js/netSync.js (modify)
- **Modify `createRemoteShipMesh()` (lines 128-142)**: Replace `buildClassMesh()` call with the new placeholder approach. The GLB override async swap already works correctly via `applyShipOverrideAsync()`. Just update the error handling path.

3. **Delete `shipParts.js`** — No longer needed.
4. **Modify `bossModels.js`** — Replace procedural builders with placeholders that preserve fire points and tentacle groups.

6. **Modify `enemy.js`** — Remove `buildEnemyMesh()`, `getFactionMats()`, faction color properties. Update spawn functions and catch handler.
7. **Modify `boss.js`** — Update `applyBossOverrideAsync()` catch handler.

## Risks
- **Kraken boss has no GLB model** — After this change it will show an error placeholder. This is intentional (makes missing asset visible) but should be noted as a known issue.
- **Race condition on load**: Entities need fire points immediately for combat. The placeholder groups must include fire points even before GLB loads. This is already handled by the current architecture (fire points are added to the group and preserved during GLB swap).
- **`shipParts.js` deletion**: If any external tool or page imports from it, deletion will break. Only `shipModels.js` imports it, so this is safe.
- **Faction colors in `enemy.js`**: The color properties (`hullColor`, `deckColor`, etc.) are only used by `buildEnemyMesh()`. Removing them is safe but verify nothing else references them (e.g., minimap icons). Grep confirms they're only used in `getFactionMats()`.
