# Plan: Bug: co-op player shows old modern ship model instead of pirate FBX

## Issue
#157 — Remote co-op player's ship renders as the old procedural modern geometry instead of the correct pirate GLB model.

## Analysis

### How local ships work (correct)
`main.js:713` calls `createShip(classCfg)` in `ship.js`. This function:
1. `ship.js:114` — builds procedural placeholder via `buildClassMesh(classConfig.key)` (immediate)
2. `ship.js:121` — calls `applyShipOverrideAsync(mesh, classConfig.key)` which loads the GLB model from `artOverrides.js` manifest, hot-swaps it onto the mesh via `loadGlbVisual()`, and preserves fire points + lights

Result: local player sees pirate GLB model after brief procedural placeholder.

### How remote ships work (broken)
`netSync.js:220` handles incoming `ship_state` messages. When a new remote player is seen (`netSync.js:256`), or when their ship class changes (`netSync.js:303`), it calls `createRemoteShipMesh(shipClass, playerIdx)`.

`createRemoteShipMesh` at `netSync.js:116-128`:
- Calls `buildClassMesh(shipClass)` — procedural geometry only
- Tints materials with player color
- **Never triggers GLB loading** — no imports of `artOverrides.js` or `glbVisual.js`

The `shipClass` string IS transmitted over the network (`netSync.js:168`) and stored on the remote ship object (`netSync.js:270`), so the data is available — just never used to load a GLB.

### Key files
- `game/js/ship.js` — `applyShipOverrideAsync()` (line 83, module-private) does the GLB swap
- `game/js/netSync.js` — `createRemoteShipMesh()` (line 116) only builds procedural geometry
- `game/js/artOverrides.js` — `getOverridePath()`, `getOverrideSize()` map class keys to GLB paths
- `game/js/glbVisual.js` — `loadGlbVisual()` loads, clones, fits, and toon-shades GLB models
- `game/js/shipModels.js` — `buildClassMesh()` builds procedural geometry by class key
- `game/assets/manifest.json` — maps class keys (destroyer/cruiser/carrier/submarine) to pirate GLB files (sloop/brigantine/galleon/manowar)

## Changes

### game/js/ship.js (modify)
- **Export `applyShipOverrideAsync`** — change `function applyShipOverrideAsync` to `export function applyShipOverrideAsync` at line 83, so netSync.js can reuse it
- **Return the promise** — currently the function calls `loadGlbVisual(...).then(...)` but doesn't return the promise. Add `return` before the `loadGlbVisual()` call (line 88) so callers can chain `.then()` after the swap completes (needed for re-tinting after GLB load)
- When no path found (line 85), return `null` instead of bare `return` for consistency

### game/js/netSync.js (modify)
- **Add import** at line 4: `import { applyShipOverrideAsync } from "./ship.js";`
- **Extract tint helper** — pull the material tinting logic (lines 121-126) into a new module-private function `applyPlayerTint(mesh, tintColor)` that traverses a mesh and lerps material colors. This is needed because tint must be re-applied after GLB swap.
- **Modify `createRemoteShipMesh`** (line 116-128):
  1. Build procedural mesh with `buildClassMesh(shipClass)` (line 117, unchanged)
  2. Apply player tint to procedural mesh immediately (placeholder while GLB loads)
  3. Call `applyShipOverrideAsync(mesh, shipClass)` and chain `.then()` to re-apply `applyPlayerTint(mesh, tintColor)` after GLB finishes loading
  4. Return mesh (unchanged — the async swap happens in-place on the same mesh reference)
- No changes to `updateRemoteShip` — both the "new player" path (line 256) and "class changed" path (line 303) already call `createRemoteShipMesh`, so both will automatically pick up GLB loading

## Order of Operations

2. Modify `netSync.js` — add import, extract tint helper, call GLB override in `createRemoteShipMesh`
3. Manual test: start a co-op game with two clients and verify both players see pirate GLB models
4. Test all 4 ship classes: destroyer→sloop.glb, cruiser→brigantine.glb, carrier→galleon.glb, submarine→manowar.glb
5. Test ship class change mid-game (if supported) — verify new GLB loads on remote client

## Risks
- **Tint application to GLB models**: The toon material conversion in `applyFlat()` (called by `loadGlbVisual`) creates new `MeshToonMaterial` instances. The tint `lerp` must run AFTER `applyFlat`, which it will since it runs in the `.then()` after `applyShipOverrideAsync` completes.
- **Fire points on remote ships**: `applyShipOverrideAsync` preserves children that are fire points or lights. Remote ships from `buildClassMesh` do have fire points in `userData.turrets`. These should be preserved correctly since the existing logic checks for them.
- **Race condition on rapid class change**: If a class change message arrives while a GLB is still loading, the old `createRemoteShipMesh` removes the mesh from scene and creates a new one. The old mesh's `.then()` callback would modify a mesh no longer in the scene — harmless since it's a detached reference, but worth noting.
- **Manifest not loaded yet**: `getOverridePath` returns `null` if manifest hasn't loaded. In that case `applyShipOverrideAsync` bails early and the procedural placeholder stays — same behavior as local ships. The manifest loads eagerly at module init, so this should only matter on very first page load.
