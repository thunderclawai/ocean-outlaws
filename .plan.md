# Plan: Bug: multi-touch input not supported on mobile

## Issue
#166 — Mobile touch input only tracks a single touch point via `e.touches[0]`, so multi-touch gestures (move + fire simultaneously) don't work.

## Analysis

### Current state
`input.js` has three touch handlers (`onTouchStart`, `onTouchEnd`, `onTouchMove`) that all read `e.touches[0]` — the first touch only. Touch events funnel into the same `mouse` object used by desktop mouse input (x, y, clicked, held, holdStart). This means:

1. A second finger touching the screen overwrites the first finger's position.
2. Releasing either finger clears `mouse.held`, killing the other finger's hold.
3. There is no concept of separate "move touch" vs "fire touch".

### How input flows through the game loop (`main.js:1144-1300`)
- `getMouse()` returns the single `mouse` object.
- `mouse.clicked` → `handleClick(mouse.x, mouse.y)` for nav waypoint or enemy targeting.
- `mouse.held` + duration > `HOLD_THRESHOLD` (200ms) → `handleHold(mouse.x, mouse.y)` for continuous movement.
- `!mouse.held && wasHeld` → `stopHold()` to stop continuous movement.
- Firing is autofire-based (`getAutofire()` always true) — doesn't depend on touch input currently. Enemy targeting does use click.

### Key insight: autofire is always ON
Since `autofire` defaults to `true` and there's no toggle key bound, weapons fire automatically at any enemy in range. The "second touch = fire" from the issue spec can be simplified: second touch = manual fire trigger OR enemy click-targeting. But the most impactful behavior is: **movement touch and fire/target touch must not interfere with each other**.

### Touch zone strategy (from issue spec)
Left half of screen = movement, right half = fire/target. This is a common mobile pattern and maps cleanly to the existing input split (movement vs combat).

## Changes

### game/js/input.js (modify)

**Add multi-touch tracking with `Touch.identifier`:**
- Add a `var touches = {}` map keyed by `Touch.identifier` → `{ id, x, y, startX, startY, startTime, zone }`.
- Zone is determined at `touchstart`: left half = "move", right half = "fire".

**Replace `onTouchStart`:**
- Iterate `e.changedTouches` (not `e.touches[0]`).
- For each new touch, store in `touches` map with its identifier, position, and zone.
- If zone is "move": set `mouse.clicked = true`, `mouse.held = true`, `mouse.holdStart`, `mouse.x/y` (backward compat).
- If zone is "fire": set a new `fireTouch` object with `{ active: true, x, y, id }`.

**Replace `onTouchMove`:**
- Iterate `e.changedTouches`.
- Look up each touch by identifier in `touches` map.
- If zone is "move": update `mouse.x`, `mouse.y` (continuous hold movement).
- If zone is "fire": update `fireTouch.x`, `fireTouch.y`.

**Replace `onTouchEnd` / `onTouchCancel`:**
- Iterate `e.changedTouches`.
- Look up each touch by identifier, remove from `touches` map.
- If zone is "move": set `mouse.held = false` only if no other "move" touch exists.
- If zone is "fire": set `fireTouch.active = false` only if no other "fire" touch exists.

**Add new exports:**
- `getFireTouch()` — returns `fireTouch` object `{ active, x, y }` (or `{ active: false }` if no fire touch).

**Backward compatibility:**
- Desktop mouse input is untouched — `mouse` object works exactly as before.
- Single-touch still works: a single touch on left half = movement (same as before), single touch on right half = fire/target.
- `getMouse()` continues to return `mouse` for all existing consumers.

### game/js/main.js (modify)

**Import `getFireTouch` from input.js** (line 5).

**Add fire-touch handling in the game loop** (around line 1181-1200):
- After the existing click/hold handling block, add:
  - `var fireTouch = getFireTouch();`
  - If `fireTouch.active` and a combat target exists and is in range: call `fireWithSound()`.
  - If `fireTouch.active` and it was just pressed (newly active): use `handleClick(fireTouch.x, fireTouch.y)` to attempt enemy targeting at the fire touch position. This lets players tap-target enemies with their fire finger.
- Track `wasFireTouchActive` (like `wasHeld`) to detect fire touch start/end transitions.

**No changes to existing movement logic:**
- The `mouse.clicked` / `mouse.held` / `wasHeld` / `handleHold` / `stopHold` flow stays identical — it just gets its data from the "move" zone touch now instead of `touches[0]`.

### game/js/nav.js (no changes needed)
- `handleClick`, `handleHold`, `stopHold` all take `(clientX, clientY)` params — they don't care about the source. No changes needed.

### game/js/weapon.js (no changes needed)
- `fireWeapon`, `aimAtEnemy` are already called from `main.js` — no touch awareness needed.

### game/js/mobile.js (no changes needed)
- `isMobile()` detection is independent of input handling.

## Order of Operations
1. **Modify `input.js`**: Add `touches` map, `fireTouch` state, rewrite touch handlers to use `changedTouches` + `Touch.identifier`, add `getFireTouch` export. Keep all existing `mouse` object behavior for desktop and backward compat.
2. **Modify `main.js`**: Import `getFireTouch`, add fire-touch handling block in game loop after existing click/hold logic. Add `wasFireTouchActive` tracking variable.
3. **Manual test on desktop**: Verify no regression — mouse click/hold movement, autofire, enemy targeting all work identically.
4. **Manual test on mobile**: Verify multi-touch — left thumb moves, right thumb targets/fires, releasing one doesn't affect the other.

## Testing
- **Desktop regression**: Mouse click sets waypoint, mouse hold does continuous movement, autofire targets enemies, QWER abilities work. No behavioral changes expected.
- **Single touch (mobile)**: Tap left half = waypoint, hold left half = continuous movement, tap right half = target enemy / fire. All should work as before.
- **Multi-touch (mobile)**: Hold left half to move + tap right half to target/fire simultaneously. Releasing fire finger doesn't stop movement. Releasing move finger doesn't stop firing.
- **Identifier isolation**: Start moving with finger A, add finger B for fire, lift finger A → movement stops but fire continues. Lift finger B → fire stops. No cross-talk.
- **Edge cases**:
  - Three+ fingers: only first move touch and first fire touch matter, extras ignored gracefully.
  - Rapid tap-tap on fire side: each tap attempts enemy targeting.
  - Touch starts on one half, drags to other half: zone is locked at `touchstart`, drag doesn't change zone.
  - `touchcancel` (e.g. system gesture): treated same as `touchend`, cleans up state.

## Risks
- **`passive: true` on touchstart**: Currently set in `initInput`. We need `e.preventDefault()` to stop scroll/zoom on touch — must change to `{ passive: false }` and call `preventDefault()`. Without this, the browser may scroll/zoom while playing.
- **iOS Safari quirks**: iOS may fire `touchcancel` on gesture conflicts (e.g. swipe from edge). The `touchcancel` handler must clean up the same as `touchend`.
- **Zone boundary**: Touches exactly on the center line (x === innerWidth/2) — pick one side consistently (e.g. right half includes center).
- **Screen resize**: Touch zones use `window.innerWidth` at event time, so orientation changes are handled naturally.
- **Autofire interaction**: Since autofire is always ON, the fire touch is additive — it enables manual targeting. If autofire is ever toggled OFF, fire touch should trigger firing. Current implementation handles both cases.
