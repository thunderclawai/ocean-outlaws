# Plan: Bug: multi-touch input not supported on mobile

## Issue
#166 — Mobile touch input only tracks a single touch point; multi-touch gestures (move + fire simultaneously) don't work.

## Analysis

### Current state (on `main`)
- `input.js` touch handlers use `e.touches[0]` — only the first finger is ever read.
- `onTouchStart` feeds the single touch into `mouse.x/y`, `mouse.clicked`, `mouse.held`.
- `onTouchEnd` unconditionally clears `mouse.held`.
- `onTouchMove` reads `e.touches[0]` for position updates.
- Event listeners use `{ passive: true }`, preventing `e.preventDefault()` which causes scroll/zoom on touch.
- There is no concept of a "fire touch" — the right-half screen cannot independently trigger weapons.

### How input flows into the game loop (`main.js`)
- `animate()` reads `getMouse()` each frame (line ~1150).
- Clicks (`mouse.clicked`) → `handleClick()` in `nav.js` → sets nav waypoint or targets enemy.
- Hold (`mouse.held` for ≥200 ms) → `handleHold()` → continuous steering.
- Release → `stopHold()` → clears nav target.
- Autofire engages when a `combatTarget` exists and is in range (line ~1292).
- There is no second-touch input path — no `fireTouch` state, no `getFireTouch()` export.

### What needs to change
1. Track every finger independently via `Touch.identifier`.
2. Split screen into two zones: left-half = move, right-half = fire.
3. Route left-half touches through existing `mouse.*` state (preserving click/hold/release behavior).
4. Route right-half touches through new `fireTouch` state that `main.js` reads for enemy targeting.
5. On release, only clear state for the specific touch that ended — don't disturb the other zone.
6. Use `{ passive: false }` so `e.preventDefault()` works (prevents page scroll during gameplay).

## Changes

### game/js/input.js (modify)

#### Add multi-touch state (after `mouse` declaration, ~line 12)
- Add `var touches = {};` — map from `Touch.identifier` to `{ id, x, y, zone }`.
- Add `var fireTouch = { active: false, x: 0, y: 0, id: -1 };` — dedicated fire-zone touch state.

#### Add zone detection helper (~line 52)
- Add `getTouchZone(clientX)` — returns `"move"` for left half of screen, `"fire"` for right half.

#### Rewrite `onTouchStart` (~line 57)
- Call `e.preventDefault()` to block page scroll/zoom.
- Iterate `e.changedTouches` (not `e.touches[0]`).
- For each touch, compute zone via `getTouchZone`, store in `touches` map by identifier.
- If zone is `"move"` and target is game canvas: feed into `mouse.x/y`, set `mouse.clicked`, `mouse.held`, `mouse.holdStart`.
- If zone is `"fire"` and no fire touch active: set `fireTouch.active = true`, record position and identifier.

#### Rewrite `onTouchEnd` (~line 80)
- Iterate `e.changedTouches`, look up each in `touches` map.
- Delete the touch from the map.
- If zone was `"move"`: only clear `mouse.held` if no other move-zone touch remains (scan remaining `touches`).
- If zone was `"fire"` and matches `fireTouch.id`: scan for another fire-zone touch to reassign; if none, set `fireTouch.active = false`.

#### Rewrite `onTouchMove` (~line 114)
- Call `e.preventDefault()`.
- Iterate `e.changedTouches`, update stored position in `touches` map.
- If zone is `"move"`: update `mouse.x/y`.
- If zone is `"fire"` and matches `fireTouch.id`: update `fireTouch.x/y`.

#### Update `initInput` event listeners (~line 154)
- Change `touchstart` and `touchmove` from `{ passive: true }` to `{ passive: false }`.

#### Add `getFireTouch` export (~line 194)
- `export function getFireTouch() { return fireTouch; }` — exposes fire-touch state to game loop.

### game/js/main.js (modify)

#### Update import (~line 5)
- Add `getFireTouch` to the import from `./input.js`.

#### Add fire-touch frame state (~line 57)
- Add `var wasFireTouchActive = false;` — tracks previous frame's fire-touch state for edge detection.

#### Add fire-touch processing in `animate()` (~line 1204, after hold logic)
- Read `getFireTouch()` each frame.
- On rising edge (`fireTouchState.active && !wasFireTouchActive`): call `handleClick(fireTouchState.x, fireTouchState.y)` to attempt enemy targeting at the touch position; if it returns `"enemy"`, set `clickedEnemy = true`.
- Update `wasFireTouchActive = fireTouchState.active` each frame.
- This integrates with the existing autofire system: once a combat target is acquired via fire-touch, autofire handles continuous weapon discharge.

## Order of Operations
1. Add `touches` map and `fireTouch` state to `input.js`.
2. Add `getTouchZone()` helper.
3. Rewrite `onTouchStart` to iterate `changedTouches`, zone-route each touch.
4. Rewrite `onTouchEnd` to only clear state for the ended touch, preserving other zone.
5. Rewrite `onTouchMove` to update correct zone based on stored touch data.
6. Change `touchstart`/`touchmove` listeners to `{ passive: false }`.
7. Export `getFireTouch()`.
8. Import `getFireTouch` in `main.js`, add `wasFireTouchActive` state.
9. Add fire-touch processing block in `animate()` after hold logic.

## Testing
- **Single touch (left half)**: tap sets waypoint, hold steers — same as before (no regression).
- **Single touch (right half)**: tap targets nearest enemy at that screen position.
- **Simultaneous move + fire**: hold left half to steer while tapping right half to target/fire — both work independently.
- **Release one finger**: releasing move finger stops steering but doesn't affect fire touch (and vice versa).
- **Touch identifier isolation**: rapidly tap and release multiple fingers — no cross-talk between zones.
- **Scroll prevention**: touching the game canvas does not scroll or zoom the page.
- **Desktop mouse**: no changes to mouse behavior — click/hold/release paths unchanged.
- **iOS Safari**: test touch events work (Safari has quirks with passive listeners).
- **Android Chrome**: test standard multi-touch behavior.

## Risks
- **`passive: false` on touchstart/touchmove**: required for `preventDefault()` but may trigger Chrome's "Added non-passive event listener" warning. This is acceptable — the game needs to block scroll.
- **Zone boundary at screen center**: a finger starting on the left that slides to the right stays in "move" zone (zone is locked at touchstart). This is intentional to prevent accidental zone switches mid-gesture, but could confuse users who expect the zone to follow the finger.
- **`isGameTarget` check**: only move-zone touches check `isGameTarget(e)` — fire-zone touches don't require the target to be the canvas element since `e.target` for multi-touch always reports the element where the first touch landed. This could cause fire touches on UI overlays to register. If this becomes an issue, zone detection should also check if the touch position overlaps a UI element.
