# Plan: Multiplayer audit: sync all pirate rework features + establish networking framework

## Issue
#150 — Full audit of every game system against the multiplayer sync layer; establish a consistent networking framework and document it in MULTIPLAYER.md.

## Analysis

### Current Multiplayer Architecture
The game uses Supabase Realtime channels for peer-to-peer multiplayer with a host-authoritative model. The networking layer is split across three files:

- **multiplayer.js** — Room management, presence tracking, host migration, broadcast primitive
- **netSync.js** — Ship position sync (12 Hz), remote ship rendering, fire event visuals, dead reckoning
- **combatSync.js** — Hit events, boss state, wave events, weather sync, pickup claims, kill feed
- **main.js** (lines 380-656) — Message routing: `onBroadcast` dispatches to `handleBroadcastMessage` / `handleCombatMessage` / `processCombatAction`

### Shared RNG
`rng.js` provides a seeded PRNG (mulberry32). All clients seed with `mpState.terrainSeed` at game start (main.js:704). This means deterministic systems (terrain generation, pickup types, enemy spawn positions) should stay in sync **if** the RNG call count stays identical across clients. This is a fragile assumption — any divergence in RNG calls causes cascading desync.

### System-by-System Audit Findings

#### 1. Palmov Terrain Compositions — MOSTLY OK, RISK
- `createTerrain(seed, difficulty)` uses the seeded RNG via `terrainComposite.js`
- In multiplayer, all clients call `seedRNG(seed)` with the shared `terrainSeed` before `createTerrain()` (main.js:704-706)
- **Risk**: `terrainComposite.js` uses its own `seededRand(seed)` function (line 26-31), NOT the shared `nextRandom()`. This means terrain placement itself is deterministic from the seed alone — GOOD.
- **Bug**: After `seedRNG(seed)` and `createTerrain()`, other systems that use `nextRandom()` (enemy spawns, pickups, weather) could diverge if any client-specific code calls `nextRandom()` between `seedRNG` and the first shared gameplay event. The GLB async loads in `addCompositeFieldVisual` complete at different times per client, but they use the local `seededRand`, not `nextRandom()` — so this is safe.
- **Conclusion**: Terrain compositions are deterministic per seed. No changes needed.

#### 2. FBX/GLB Ship Models — BUG FOUND
- `netSync.js:128-142` creates remote ship meshes via `createRemoteShipMesh()` which calls `buildClassMesh()` + `applyShipOverrideAsync()`.
- The `shipClass` is sent in `ship_state` messages (netSync.js:182) and presence data.
- **Bug**: When a client first receives a `ship_state`, the remote ship is created with the correct `shipClass`. However, the initial ship class comes from presence `shipClass` field set during lobby, but the `ship_state` message also sends `shipClass`. If a player changes class between lobby and game start, the initial `ship_state` will have the correct class, but there's a brief window where no mesh exists yet.
- **Conclusion**: Ship model sync works correctly. The `shipClass` is sent every `ship_state` update, and class changes trigger mesh rebuild (netSync.js:313-322). Minor: remote ships show a magenta placeholder box briefly until GLB loads — cosmetic only.

#### 3. Cannon/Weapon Fire — PARTIAL SYNC, BUG
- `sendFireEvent()` broadcasts weapon key, origin, and direction (netSync.js:188-198)
- Remote projectiles are visual-only spheres (netSync.js:247-258) — they don't hit anything
- Actual damage is synced via `sendHitEvent()` when the firing client's projectile hits an enemy locally (weapon.js:356-358, main.js:720)
- **Bug**: `sendFireEvent` sends `weaponKey` but `spawnRemoteProjectile` ignores it — always uses the same blue sphere geometry (remoteProjGeo). Remote players see generic blue projectiles instead of cannon/chain-shot/fire-bomb visuals.
- **Bug**: Remote fire events don't include weapon-specific properties (gravity, speed, water-level), so the visual trajectory is wrong for non-cannon weapons.
- **Missing**: Remote fire events don't play weapon sounds on receiving clients.

#### 4. Enemy Factions — OK
- Enemy state sync (combatSync.js:201-226) includes `faction` field per enemy
- Host drives all enemy AI; clients receive positions via `enemy_state` at ~5 Hz
- Faction-specific behavior (pirate rush, navy circle, merchant flee) runs only on host
- **Conclusion**: Works correctly. All clients see same faction labels and enemy positions.

#### 5. Gold Economy — BUG / DESYNC
- Gold is earned locally per-client on enemy kills (main.js ~line 162: `addGold(upgrades, gld)`)
- The `onDeathCallback` (main.js:143-165) fires on ALL clients when an enemy dies (since `damageEnemy` is called locally or via combat sync)
- **Bug**: When the host kills an enemy, the host gets gold from `onDeathCallback`. When the kill is broadcast to clients via `enemy_death`, those clients also run `damageEnemy` locally which triggers the same `onDeathCallback`, awarding gold again. So ALL players get gold for every kill regardless of who killed it — this might be intentional (shared loot) but is undocumented.
- **Missing**: Gold drops from pickups are client-local — whoever picks up a gold crate gets the gold, and other clients just see the crate disappear. This is correct behavior but needs documenting.
- **Missing**: Port shop purchases are entirely client-local (portScreen.js operates on local `upgrades` state). No sync needed — each player has their own upgrades.

#### 6. Voyage Chart — NOT SYNCED, BY DESIGN
- `voyageChart.js` and `voyageData.js` are roguelite run systems
- Multiplayer mode uses `startMultiplayerCombat()` (main.js:684-734) which bypasses the voyage chart entirely — it goes straight to wave combat with a shared terrain seed
- **Conclusion**: Not applicable to multiplayer mode currently. If multiplayer roguelite runs are added later, the host would need to broadcast node selection.

#### 7. Port Shop — NOT SYNCED, BY DESIGN
- Port visits don't occur in multiplayer (no voyage chart → no port nodes)
- Each player's upgrades are private (card picker between waves, main.js:572-583)
- **Conclusion**: Correct. Document as "client-local, private per player."

#### 8. Day/Night Cycle + Ship Lanterns — OK (via #141)
- Host broadcasts `weather_sync` at ~2 Hz (combatSync.js:97-108) which includes `timeOfDay`
- Non-host clients apply `setTimeOfDay()` (main.js:617-618)
- Ship lanterns update from `getNightness(dayNight.timeOfDay)` (main.js:1285) — local per client but driven by the synced `timeOfDay`
- Remote ship lanterns are NOT synced — remote ships have no lantern. But remote ships are tinted by player color, so this is cosmetic.
- **Conclusion**: Core day/night is synced. Ship lanterns are local only (acceptable).

#### 9. Weather Effects — OK (via #141)
- Host drives weather changes (main.js:1291-1295) and broadcasts `weather_change` + periodic `weather_sync`
- Non-host clients apply weather via `setWeather()` / `setTimeOfDay()` (main.js:609-619)
- Rain, fog, lightning are all locally computed from the weather preset — same key = same visuals
- Wave amplitude is part of the weather preset, affecting ocean height
- **Conclusion**: Weather is synced correctly.

#### 10. Infamy System — CLIENT-LOCAL, NEEDS DOCUMENTATION
- `infamy.js` stores Infamy in localStorage — it's a meta-progression system
- In multiplayer, `awardRunInfamy()` runs on each client independently at game over/victory (main.js:590, 601, 637, 648)
- Each player earns their own Infamy based on their local kill count (`runEnemiesSunk`) and gold (`runGoldLooted`)
- **Bug**: `runEnemiesSunk` increments in `onDeathCallback` which fires for ALL kills (not just the local player's kills). So all players get the same Infamy for enemies sunk.
- **Conclusion**: Should be documented as "client-local, earned independently per player."

#### 11. Buoyancy + Ocean Waves — OK
- `getWaveHeight()` in ocean.js is a pure math function of (x, z, time, waveAmp, waveSteps)
- `elapsed` (clock time) drives the wave function — all clients use the same `THREE.Clock`
- Wave amplitude comes from the synced weather preset
- **Risk**: `elapsed` is measured from each client's page load, NOT from a shared timestamp. If clients load at different times, waves will be out of phase. However, this is cosmetic — ship positions are synced via `ship_state`, and buoyancy for remote ships is computed locally from `getWaveHeight()` (netSync.js:384-404).
- **Conclusion**: Acceptable. Document that ocean phase is cosmetic-local, position is authoritative.

#### 12. Hitbox/Collision Shapes — OK
- Ship OBB (weapon.js:324-337) and player OBB (enemy.js:581-592) are fixed constants
- Hit detection runs on each client locally — the firing client detects the hit and broadcasts `sendHitEvent`
- **Risk**: Since enemy positions are interpolated on non-host clients (dead reckoning), a non-host player's hit detection may disagree with the host's view. Shots that visually hit on one client might miss on another.
- **Conclusion**: Current design is "shooter-favored" — whoever fires detects the hit locally and broadcasts damage. This is an acceptable tradeoff for a casual co-op game. Document it.

#### 13. Audio State — CLIENT-LOCAL, CORRECT
- All audio is local: engine, ambience, music, weapon sounds, UI sounds
- No audio state is sent over the network
- **Bug (minor)**: Remote player fire events (`fire` messages in netSync.js) spawn visual projectiles but don't play weapon sounds. Players can't hear other players shooting.
- **Conclusion**: Audio is correctly client-local. Add remote weapon sounds for fire events.

#### 14. Card Picker Upgrades — PARTIAL, NEEDS FIX
- Between waves, each player sees their own card picker (main.js:572-583)
- Upgrades are applied locally via `applyFreeUpgrade()`
- **Bug**: The game is NOT paused for other players when one player is choosing cards. The `cardPickerOpen` flag only freezes the local game loop (main.js:1198). Other players continue fighting/moving. This means:
  - If player A finishes a wave and opens card picker, player B who also finished sees it
  - But if they finish at slightly different times (due to network latency), wave timing can diverge
- **Actually OK**: Wave completion is broadcast by the host as a single `wave_complete` event (main.js:1421-1465). All clients receive it simultaneously and each opens their own card picker. The `gameFrozen`/`cardPickerOpen` freeze is local, but since all enemies are dead at wave_complete, there's nothing dangerous happening.
- **Conclusion**: Card picker is correctly per-player. The game doesn't actually need to pause globally since enemies are dead between waves. Document as "client-local, each player upgrades independently."

#### 15. Crew Pickups — BUG, NOT SYNCED
- `crewPickup.js` has no multiplayer sync at all — no broadcast on collection
- When a crew pickup spawns (from enemy death callback or boss defeat), it spawns on ALL clients at the same position (since the death callback fires on all clients)
- **Bug**: Multiple players can each collect the same crew pickup, duplicating crew officers
- **Fix needed**: Crew pickups should use the same claim/confirm pattern as regular pickups — player broadcasts `pickup_claim`, host confirms with `pickup_confirmed`, only the confirmed player gets the officer
- The `crewPickupMgr` has an `onCollect` callback but no network equivalent of `setPickupCollectCallback`

#### 16. Rejoin Flow — PARTIAL, MISSING STATE
- Host sends `rejoin_state` (main.js:423-434) with: terrainSeed, wave, waveState, weather, timeOfDay, enemies, boss, hostId
- **Missing from rejoin_state**:
  - Pickup positions (both resource pickups and crew pickups)
  - Gold/upgrade state (the rejoining player starts with nothing)
  - The rejoining player's run stats (enemiesSunk, goldLooted)
  - Active merchants/crates
  - Player health (rejoining player gets full HP from class defaults)
- These are acceptable losses for a casual game but should be documented.

### Bandwidth Analysis
Current message types and frequencies:
- `ship_state`: 12 Hz per player (rate-limited, threshold-gated) — ~500 bytes × 4 players = 24 KB/s
- `enemy_state`: ~5 Hz, host only — variable size, ~50 bytes per enemy × 12 max = 3 KB/s
- `fire`: event-driven, ~1-2/sec per player — ~100 bytes each
- `boss_state`: ~5 Hz, host only — ~100 bytes = 0.5 KB/s
- `weather_sync`: ~2 Hz, host only — ~50 bytes = 0.1 KB/s
- `hit`, `enemy_death`, `kill_feed`, `wave_event`: event-driven, sporadic
- **Total estimate**: ~30-40 KB/s peak with 4 players in combat

### Missing Networking Framework
No documentation exists for:
- How to add sync to a new feature
- What's host-authoritative vs client-local
- Message naming conventions
- Bandwidth budgets

## Testing
- **Terrain sync**: Open two browser tabs, create/join same room, verify identical island placement
- **Ship models**: Verify each player sees correct GLB model for other players' ship classes (not magenta box after loading)
- **Weapon fire visuals**: Fire each weapon type (cannon, chain shot, fire bomb) and verify remote player sees correct projectile color/shape/trajectory
- **Remote weapon sounds**: Verify other players' shots are audible
- **Crew pickups**: Kill an enemy that drops a crew pickup, have two players race to collect it — only one should receive the officer
- **Weather sync**: Change weather on host (wait for random change or trigger storm), verify client matches
- **Day/night sync**: Play for >3 minutes, verify both clients show same time of day
- **Gold economy**: Kill enemies and verify gold amounts are correct per player
- **Wave progression**: Play through multiple waves, verify wave numbers stay in sync
- **Rejoin flow**: Disconnect a client mid-game, rejoin via room code, verify terrain/wave/weather/boss state restores
- **Host migration**: Kill the host's browser tab, verify new host takes over and game continues
- **10+ minute stability**: Play a full 10-wave multiplayer session and check for desync (enemy positions drifting, wave state mismatch)

## Risks
- **RNG divergence**: The shared seeded PRNG is fragile — any client-specific code path that calls `nextRandom()` will desync all subsequent random values. The audit found this is currently safe because terrain uses its own seeded function, but future features must be careful.
- **Crew pickup sync adds complexity**: The claim/confirm pattern requires host roundtrip, which adds latency to crew collection. In practice this is ~50-100ms which is acceptable.
- **Remote projectile visual change**: Changing from a single sphere to weapon-specific geometry means importing weapon config into netSync.js, creating a dependency. Keep it simple — just color/speed/gravity, don't import the full weapon module.
- **No test infrastructure**: There are no automated tests. All testing is manual in browser. The audit verification relies entirely on manual playtesting with multiple browser tabs.
- **Async terrain loading**: GLB model loads are async and complete at different times per client. If any future code runs `nextRandom()` in an async callback, it will desync the shared RNG. This is currently safe but fragile.
